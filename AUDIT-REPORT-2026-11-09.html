11. Recommendations and production-readiness

Assessment: ready for small and medium shops (up to a few thousand products) after the quick fixes; not ready for very large catalogues or high scale yet.

  1. Before go-live (small effort): S-N1 (add permissions to whatsapp.messages, qr.pending/recent, orders.board; drop kitchen.view from RECORD_PERMS), K-1 (restock only what was taken), N-1 / K-4 (argument checks — 25 handlers returning 500, including the public placeOrder), S-N2…S-N5, K-7 idempotency.
  2. Before onboarding large shops: P-1 (page/compress the public menu), P-2 (server-side product search/paging, one catalogue load per session, dashboard low-stock from the server), P-5 (weekSummary / movements in SQL).
  3. For cost and scale: P-3 (fewer sequential DB round trips per bill — also brings checkout/QR/save p95 under 10 ms), P-4 (platform-DB writes per bill are back after the revert), P-6 (skip events.ticket on Catalyst, de-duplicate dashboard calls), add response compression.
  4. After deploy: verify /ip-check (rate limits rely on the gateway’s address), set PASSWORD_PEPPER and STRATUS_PRIVATE_BUCKET, rotate the exposed secrets, measure real Turso latency from Catalyst India.

12. Method, environment and limits

  • Code: the current working tree (not a previous build). Production frontend built from it today (vite build, catalyst mode) and served with the API from the same origin.
  • Servers: the real Express app (createApp) in its own Node process, configured like the Turso setup in catalystEnv.ts; the database is the project’s fake Turso (real SQLite behind the production Hrana-over-HTTP driver) in a separate process — so server CPU excludes database execution but includes building and parsing every database request.
  • Wall-clock vs CPU: “wall” = time from request in to response out at the server (and client-side totals for flows/pages); “CPU” = process.cpuUsage() user + system of the API process for that request, measured with one request at a time. For pages (parallel requests) only the page total is exact; per-call CPU there overlaps.
  • Network: local, no TLS. The “10 ms DB RTT” columns add 10 ms to every database call to approximate Turso over the network; real Turso latency from Catalyst India was not measured.
  • CPU accuracy limits: Apple M3 laptop (performance + efficiency cores, no core pinning on macOS), Node 18 (project targets Node 24), and macOS background work (mediaanalysisd, browser) running during the test; p50 is reliable, p95/max can be inflated by scheduling. Catalyst’s real CPU (128 MB function, different CPU) will differ.
  • Browser: desktop Chromium in the Claude app; the resource-timing buffer holds 250 entries, so pages with >160 calls show a lower bound; the pane was hidden, so render-frame timings were not used (search times use timers).
  • Data: realistic synthetic shops (restaurant with 60 dishes, 40 customers, 8 tables, 4 purchases, 40 bills before the measured run; supermarket with 50,006 products in 10 categories, variants, barcodes, stock). Test credentials were created by the test harness only for these local servers.
  • Not tested: real WhatsApp/Meta, real push delivery, Stratus buckets, Catalyst Data Store/ZCQL, real gateway IP behaviour, multi-device concurrency across machines, DoS/long soak.
  • No code changes were made during this audit. Temporary test files were created only under backend/test/zz-* and deleted; no processes left running.
