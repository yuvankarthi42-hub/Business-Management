How it was measured

  • App CPU = process CPU time for the request minus the time inside the SQLite engine. This is the part the 10 ms CPU limit counts. It includes our code, JSON encoding and the database driver's own JavaScript. One request ran at a time, so each call's CPU is its own.
  • DB execution = time inside the SQLite engine (sql.js, in-process). It is not added to app CPU. Query count = SQL statements run. Outgoing requests = database round trips (each is one HTTPS request on Turso).
  • DB / network wait is not measurable here: the test database runs inside the same process, so there is no network. On Turso, add ≈ one network round trip per outgoing request (region-dependent). Local response = total time on this machine (app + DB), not a production latency.
  • Data: normal = 300 items, 2,000 bills over 90 days, 200 customers, 2 branches, 8 shops. Large = 2,000 items, 10,000 bills, 1,000 customers, 32k stock movements, 30 shops. Both include variants, add-ons, wholesale prices, HSN, expiry batches, suppliers and purchase bills (one voided), returns, cancelled bills, expenses, loyalty points (some expired), dine-in orders with KOTs, QR orders (accepted / rejected / pending), staff pay and attendance, specials, a campaign and a support ticket.
  • Runs: (1) the real web app driven page by page in a browser on normal data (labelled page/action); (2) a script calling all 178 APIs — reads ×20, writes ×10, exports ×3 — on a fresh server for each data size. Cold = first call in a fresh server process (empty caches, unwarmed JIT); warm = the rest.
  • Colours: red > 10 ms, amber 8.5–10 ms.
