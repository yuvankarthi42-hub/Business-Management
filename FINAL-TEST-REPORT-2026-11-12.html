Next step: deploy to a Catalyst test environment with real Turso, repeat the hotel and silks loads there, read the real CPU in Catalyst’s logs, then run one pilot shop for a few days.

Where these numbers come from

Measured on this machine (simulated hosting). The real app (the same code as commit 836377e) runs in its own Node 18 process. The database is a fake Turso: real SQLite (sql.js) behind the same Turso HTTP protocol, in a second process, so the app’s CPU does not include database work. A 10 ms delay can be added to every database request to imitate a nearby Turso region.

Not measured: nothing was deployed to Cloudflare, Catalyst or Turso. There is no login for either platform on this machine, and the backend has no Cloudflare Workers version (it runs on Node, as Catalyst needs). Platform limits and prices come from their official pricing pages (retrieved 11 Nov 2026), applied to the measured numbers.

CPU: “server CPU” = the app process’s CPU time during each request, taken from calls made one at a time. This Mac has fast and slow cores and lowers its speed between bursts, so CPU is most trustworthy at 0 ms database delay on a quiet machine; see the CPU experiment below.

Database performance and bottlenecks

  • Database trips per action: a 10-item checkout makes 19 trips; the largest single API makes 43 (hotel). With a real Turso region 10–30 ms away, a checkout spends about 0.2–0.6 s waiting on the database: this, not CPU, is most of a bill’s response time.
  • Full table scans: the GST report reads every purchase and return ever made (schema audit M-2), and the 32 single-column business_id indexes cost index writes on every bill without helping any query (M-1). Both are still open from the schema audit.
  • Write lock: each shop’s writes queue in arrival order (P-4). With 10 silks counters billing at once, bills wait for each other: see the bill time p95 in the silks card.
  • Growth: the silks database grew by about 10.6 MB per 1,000 bills of 20 items (measured), i.e. about 127 MB per busy day of 12,000 bills.
  • Test database limit (not the app): the local sql.js test database faulted (“memory access out of bounds”) after about 4,000 silks bills in one process, which ended two earlier silks runs. Memory stayed flat at 130–210 MB, so the cause is inside sql.js. Real Turso has no such limit; each big shop was therefore run on its own fresh test database.

Cloudflare deployment

Status: not deployed (simulated). The backend is an Express app for Node, which is what Catalyst runs. Cloudflare Workers would need a Workers entry point and replacements for three Catalyst services the app uses: the Catalyst Cache (→ Workers KV or a Turso table), Stratus file storage (→ R2) and the daily Cron function (→ Cron Triggers). Database access already uses Turso’s HTTP protocol, which works from Workers unchanged.

What the measurements say about Workers limits:

  • Free plan, 10 ms CPU per request: billing and most screens fit at 0 ms delay on this laptop (checkout 6.4 ms for 10 items), but the 11 hotel cases and 5 large-shop cases in the table above would be stopped on the free plan. The Maligai 60-item checkout (13 ms) is one of them, so a maligai-sized shop cannot use the free plan for billing.
  • Free plan, 50 subrequests per request: every database trip is one subrequest. The largest single API makes 43 trips (hotel); every API fits.
  • Free plan, 100,000 requests a day per account: see the free-tier section; the daily requests of a busy shop are mostly screens checking for changes every 30 s.
  • Paid plan ($5/month): 30 s CPU per request and 10,000 subrequests: every API measured fits, including the whole-shop export.

What decides the free tier:

  • Turso’s free plan allows 100 databases in total, and this app uses one per shop plus one platform database: at most 99 shops on one free Turso account, whatever their size.
  • Turso rows written (10 million a month) are the next limit for busy shops: every bill line writes its line, stock row, stock movement and change-log entries.
  • Cloudflare’s free plan also stops any request above 10 ms CPU, so shops whose daily work includes such requests (see the table) need the paid plan regardless of volume.
  • Catalyst’s free 25,000 GB-seconds a month is counted from function running time (including database waits), not CPU, so database distance matters more there.

Remaining limitations

  • No Cloudflare, Catalyst or real Turso measurement: every number here is from this machine.
  • Loads are time-compressed: the same bill counts as hotel 24 h, maligai 8 h and silks 2 h, sent within minutes. Real days spread them out, so real response times are lower than the load runs show; real CPU per bill is close to the one-at-a-time numbers.
  • Silks was shortened from 8 h to 2 h of bills to have the report ready on time.
  • CPU on this Mac depends on its fast/slow cores and power saving; numbers at 10 ms delay are probably 2–5× too high (see P-10b).
  • Push notifications were not sent (no push keys on the test server); WhatsApp is the app’s own simulated Meta review, not Meta.
  • The free-tier and cost figures are estimates from measured per-bill numbers and published limits, not platform bills.
  • Page loading times were taken in the in-app browser on this machine with the database 10 ms away; a phone on a mobile network will be slower.
