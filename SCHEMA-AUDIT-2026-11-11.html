How this was checked

  • Read the full source schema (1,014 lines), all 13 shop and 3 platform migrations, and backend/setup/tables.json.
  • Counted, for every column, where the backend code mentions it (generated files excluded), then checked each low count by hand.
  • Listed every index and ran EXPLAIN QUERY PLAN on the generated shop schema (server/turso/shop.sql) in SQLite.
  • Confirmed in code that the SQL schema is only used with one database per shop (PerShopDatabases; SingleDatabases is only the Data Store and in-memory test store).
  • Traced every hard delete, because a foreign-key index is needed only when it is queried or its parent row can be deleted.

Confirmed issues

H-1HighConfirmed

Profit reports use today's cost price, not the cost at billing time

order_items.cost_minorproducts.cost_minorsale_return_items
Issue
Every bill line saves the item's cost when it is billed, but every profit and cost-of-goods report joins to the product's current cost. The saved cost is never read.
Why it matters
If the owner edits an item's cost today, last month's profit changes too. A report for a closed period should not move.
Change
Add up cost of goods from order_items.cost_minor. For returns, take the cost of the sold line through sale_return_items.order_item_id.
CPU / DB calls
Lower. The join to products for cost is no longer needed; still one request.
Risk / migration
No migration: the column already exists and is filled. Past-period profit numbers will change (they become correct). Bills made while an item's cost was still 0 will show cost 0. Needs the owner's decision because report values change.

Evidence: cost saved at billing in backend/src/domain/orders.ts:208 and :216; reports join current cost in backend/src/modules/reports.ts:380–391.

M-1MediumConfirmed

32 single-column business_id indexes in every shop database

order_itemsorder_item_addonsorder_item_batcheskitchen_ticket_itemscustomer_pointspurchase_itemsstock_batchespurchases+ 24 more
Issue
Each shop has its own database, so business_id holds the same value in every row. An index on it cannot narrow anything down, yet it is updated on every insert.
Why it matters
A 20-line bill writes 20 or more extra index entries for order_items alone, plus the add-on, kitchen and points rows. The query planner also picks these indexes: the GST purchases query uses ix_purchases_business_id, which reads every row. Fix B-4 dropped the one on branch_stock for the same reason.
Change
One migration that drops these 32 indexes. Keep the column (the code shares it with the Data Store) and keep every composite index.
CPU / DB calls
App CPU and DB calls unchanged. Database write time goes down. No query gets slower: these indexes already mean a full scan.
Risk / migration
Low. Index drops only, recreatable. Confirm with EXPLAIN over the test suite's queries before dropping. Turso only.

Evidence: one business per database in backend/src/db/databases.ts; the full list of 32 is in the appendix.

M-2MediumConfirmed

The GST report reads every purchase and return ever made

purchasessale_returns
Issue
purchases has only a business_id index. sale_returns has (business_id, branch_id, created_at), but the GST query has no branch filter, so only the useless first column is used.
Why it matters
Every monthly GST report reads all history. It gets slower every year the shop runs.
Change
Add an index on purchases (purchase_date) and one on sale_returns (created_at).
CPU / DB calls
Same calls. Each read covers one month instead of all history. One extra index write on two low-volume tables.
Risk / migration
Low. Index-add migration only.

Evidence: EXPLAIN shows SEARCH purchases USING INDEX ix_purchases_business_id (business_id=?) and SEARCH sale_returns USING INDEX ix_sale_returns_business_id_branch_id_created_at (business_id=?).

M-3MediumConfirmed

orders.tax_breakup_json is written on every bill and never read

orders
Issue
Each bill runs JSON.stringify on its tax lines and stores the text. Nothing reads it.
Why it matters
CPU and storage on the busiest write. GST per line is already stored relationally in order_items.taxable_minor and tax_minor.
Change
Stop writing it. Keep the column: dropping a column rewrites the whole orders table.
CPU / DB calls
Lower CPU and fewer bytes on every bill.
Risk / migration
Very low, no migration. The data export includes this column, so old exports have it and new ones will not.

Evidence: the only reference in the backend is the write in backend/src/domain/orders.ts:612.

M-4MediumConfirmed

Two duplicate checks exist only in code, with no database constraint

purchases.client_uuidsuppliers.name_key
Issue
purchases.client_uuid is nullable and not unique; suppliers.name_key is not unique. The schema says "checked by the API": the code looks first, then inserts.
Why it matters
Two retries arriving together can both pass the check: a purchase saved twice adds stock twice; a supplier can be created twice. Bills, payments and returns already have UNIQUE keys for this.
Change
UNIQUE index on purchases (client_uuid) WHERE client_uuid IS NOT NULL and on suppliers (name_key). Data Store: set IsUnique on both columns.
CPU / DB calls
Unchanged; one index entry per purchase or supplier.
Risk / migration
Medium. Existing duplicates must be found and resolved first, or the migration fails.

Evidence: check-then-insert in backend/src/modules/purchases.ts:228 (purchases) and :119 (suppliers); no UNIQUE in migration 0004.

S-1SuggestionPartial evidence

Possibly extra indexes on the busiest tables

orders · 16payments · 8stock_movements · 7customer_points · 6
Issue
Some single-column indexes look covered by composite ones (orders.customer_id, orders.branch_id). Others sit on parents that are never hard-deleted (created_by, updated_by, price_list_id).
Why it matters
Every bill updates all of them.
Change
Log every SQL statement during the full test run, EXPLAIN each one, list indexes never used, and drop only those. Keep indexes whose parent can be deleted (table_id, order_item_id, category_id, media ids, template_id): EXPLAIN shows ix_orders_table_id is used when a table is removed.
CPU / DB calls
Fewer index writes per bill; app CPU unchanged.
Risk / migration
Low once proven; index drops only.

S-4Suggestion

Small consistency points

  • expenses.expense_date is a DATETIME while purchase_date and paid_on are DATE.
  • daily_specials has no uniqueness on (product, date, branch); the code decides it.

Checked and correct (not issues)

  • Copied totals: orders.paid_minor / balance_minor / returned_minor and customers.points_balance, kept for fast reads beside their ledgers.
  • Tables in both databases: media_files, secrets, whatsapp_templates, whatsapp_messages (shop rows in the shop DB, platform rows in the platform DB).
  • Sign-in names across databases: login_names is claimed first, bound after the user is saved, undone on failure, and unbound claims are cleaned daily.
  • References across the two databases: stored as plain columns with comments, not foreign keys that SQLite could not check.
  • Composite uniqueness: uniq_key columns, needed because Catalyst's IsUnique works on one column.
  • Bill snapshots and money: snapshot names on bill lines, money in paise, quantities in thousandths, rates in basis points.

Assumptions and limits

The Catalyst Data Store's real indexes and ZCQL query plans cannot be inspected from here. For it, only the match between tables.json and the schema was checked (64 tables, none missing or extra).

Index gains in M-1, M-2 and S-1 are database write and read time, not app CPU. They should be measured on real Turso.

Recommended order

  1. H-1: decide first, because past profit numbers will change.
  2. M-3: code change only, no migration.
  3. M-1 and M-2: together, in one index migration.
  4. M-4: find existing duplicates first, then the migration.
  5. S-1: after the final test run, from the logged queries.
  6. Low items: together, later.
